## What is this?

Ricrac is an issue tracker for agents.
It has no interface of its own: agents use it through the MCP server (`/mcp`) and the REST API
(`/v1`), and people sign in with Google to a small dashboard to manage their workspaces, API keys
and OAuth apps. README.md covers features and configuration.

Two apps: `apps/server` is the Rust server (Axum, sqlx on Postgres) and `apps/web` the dashboard
(Vite, React, TanStack Router + Query, Tailwind, shadcn), embedded into the server binary at
build time. Production is the `Ricrac` project on Unbind: the `ricrac` service (this repo's
Dockerfile) and a `postgres` database service.

## Repo Structure:

### apps/server (Rust, Axum, sqlx 0.8 on Postgres)

- `ops/` holds every operation of the tracker, defined once with `op(name, access, routes,
  description, handler)`. `ops::all()` feeds the MCP tools (`mcp.rs`), the REST routes, the generic
  `POST /v1/ops/{name}` and the OpenAPI document (`rest.rs`). MCP lists the everyday operations
  (`mcp::CORE`) as tools and reaches the rest through `find_operations` and `call_operation`, so a
  session doesn't start with every definition; `/mcp?tools=all` lists them all. A handler is
  `async fn(ctx: Ctx, args: Args) -> ApiResult<Value>`; `Args` derives `Deserialize` and
  `JsonSchema` with `#[serde(rename_all = "camelCase", deny_unknown_fields)]`, and its doc
  comments are what agents read.
- `ops/resolve.rs` turns what agents pass (names, keys, identifiers like ENG-123, "me", links)
  into ids and checks the caller may see the thing; errors list the valid options.
  `ops/filter.rs` is the issue filter language, used by `list_issues`
  and custom views. `ops/events.rs` writes issue history, notifications, webhook deliveries and
  the audit log inside the change's transaction. `ops/util.rs` has the nullable-argument helper,
  dates and durations, paging, slugs and Markdown patches.
- `ctx.rs` is the caller: `Caller` is the user, token scopes and the workspaces the token reaches
  (one, several or all); `Caller::ctx` picks the one a call acts in (the `workspace` argument,
  links among the arguments, or the only one) and gives a `Ctx`: user, workspace, role (owner,
  admin, member, guest), scopes and the teams they can see (private teams only for their members;
  guests only their teams). Operations defined with `account_op` run with the `Caller` instead.
- `migrations/0002_refs.sql` defines `user_ref`, `team_ref`, `state_ref`, `issue_ref`,
  `project_ref`, ... SQL functions: every response shows a referenced thing in the same short JSON
  form. Responses are built in SQL with `jsonb_build_object` (at most 100 arguments per call;
  join two with `||`).
- `oauth.rs` is the OAuth 2.1 server (discovery, dynamic registration, client ID metadata
  documents, dashboard apps, PKCE, rotating refresh tokens, revocation) and the bearer check for
  `/v1` and `/mcp`, which also takes API keys (`rr_key_...`). Grants and keys reach the
  workspaces chosen when they were made, or all of the user's (`workspace_ids` NULL).
- `google.rs` is sign-in with Google; `account.rs` the dashboard's JSON API under `/api`
  (workspaces, invitations, API keys, OAuth apps, connected apps, OAuth consent). Its types are
  exported to TypeScript with ts-rs.
- `jobs.rs` runs the automations every minute (auto-archive, auto-close, trash, snoozes, due
  dates, cycles, recurring issues from templates) and delivers webhooks. `seed.rs` is what new workspaces and teams start with.
- `files.rs` serves uploads; `spa.rs` serves `apps/web/dist`.

### apps/web (Vite, React, TanStack Router + Query, Tailwind, shadcn)

`src/routes` are the pages (file routes), `src/api` the API client and queries,
`src/components/ui` are shadcn components. `src/api/types` is generated by `cargo test` in
apps/server.

## Conventions

- Output and arguments are camelCase. Timestamps are ISO 8601 UTC.
- `save_*` creates without `id` and updates with it. Optional fields left out stay as they are;
  `null` clears them (`Option<Option<T>>` with `#[serde(default, deserialize_with = "nullable")]`
  and `#[schemars(with = "Option<T>")]`).
- Lists take `limit` and `cursor` and answer `{ nodes, pageInfo: { hasNextPage, endCursor } }`
  through `util::Page`.
- Reading a NULL jsonb into `serde_json::Value` fails: select `Option<Value>` or `coalesce`.
- Deleting issues, projects, initiatives and documents moves them to the trash (`trashed_at`);
  the trash is emptied after 30 days.
- Every mutation runs in one transaction, records history (issues) and emits a webhook event
  (`events::emit`) with the entity's JSON.

## General Rules:

- Keep it simple. Do not overcomplicate things.
- Do not leave paragraphs of comments on top of the code. You should try to avoid them as much as possible with understandable function names and code. If they are necessary even then, make them concise. Remove such comments when you come by them in the codebase. Comments should always move with code, not be left behind.
- Use guard statement patterns in any code you write.
- Do not edit generated code: `Cargo.lock`, `bun.lock`, `src/routeTree.gen.ts`, `src/api/types`.
  Never edit an applied migration in `migrations/`, add a new one.
- Do not write useless tests; tests should cover input/output behaviour.
- Reinvent the wheel but do not reinvent the car. If you are solving a simple problem do not
  introduce a library. If you are solving a complex but common problem, there is likely a
  modern library for it, if so, use it.
- Do not start editing code in response to a question. We'll tell you when to edit code.
- If we are missing a glaring issue when we ask you to do something, do not hesitate to
  point it out.
- Never commit or push code unless explicitly asked to do so.
- Never make a PR unless explicitly asked to do so.
- Do not insert yourself into our code, commits or PRs in any way. Our codebase is not your
  ad space.
- When a deploy changes required env vars, deploy the code first and change the variables
  after. Unbind restarts the running pod on every variable change.
- After you make code changes, run the checks (see below) and fix what they raise.

## Development

Needs Rust stable, Bun and Docker (for Postgres).

    docker compose up -d                       # Postgres on localhost:5436
    cd apps/server && cargo run                # with the variables from .env.example exported
    cd apps/web && bun install && bun dev      # http://localhost:5173, proxies to the server

Checks (`cargo test` needs the compose Postgres; `.cargo/config.toml` points `DATABASE_URL` at
it and each test gets a throwaway database):

    cd apps/server && cargo fmt && cargo clippy --all-targets && cargo test
    cd apps/web && bun run lint && bun run build

The end-to-end tests live in `apps/server/src/e2e/`: each starts from `world()` (a workspace
"acme" owned by Ann with the team ENG) and calls operations with `call`, `fails` and
`try_call`; `http.rs` goes through the real router (REST, OAuth, MCP). Behaviour changes need a
test there.

For browser checks use headless Chromium through `playwright-core`, never the editor's preview tab.
